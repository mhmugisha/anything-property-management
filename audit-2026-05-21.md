## A. Structural Vulnerabilities in Payment Routes

### A.1 `apps/web/src/app/api/payments/route.js` — POST handler

#### Multi-step writes

**Case A — Invoice payment** (lines 131–315):
1. `INSERT INTO payments` → returns `payment`
2. `INSERT INTO payment_invoice_allocations`
3. `UPDATE invoices` (paid_amount + status)
4. `postAccountingEntryFromIntents(...)` — GL post
5. `createArrearsRecoveryFee(...)` — arrears fee (swallowed in try/catch)

**Case B — Advance payment** (lines 320–473):
1. `INSERT INTO payments` → returns `payment`
2. `postAccountingEntryFromIntents(...)` — GL post
3. `autoApplyAdvancePaymentsForTenant(tenantId)` — swallowed in try/catch

#### Transaction coverage

**None.** All five steps in Case A and all three steps in Case B are independent `await` calls with no wrapping transaction. There is no `sql.transaction()` anywhere in this handler.

#### Half-committed failure paths

| Failure point (Case A) | DB state left behind |
|---|---|
| Step 2 fails (alloc insert) | Payment row exists, invoice not updated, no GL |
| Step 3 fails (invoice update) | Payment + alloc exist, invoice not updated, no GL |
| Step 4 fails (GL post) | Payment + alloc + invoice update committed, **no accounting entry** |

The GL post throws on failure (`throw new Error(...)` at line 248), which causes the handler to return 500 — but the three prior DB writes are already committed and cannot be rolled back.

**Case B** has the same problem: if `postAccountingEntryFromIntents` throws, the advance payment row exists with no GL entry. The auto-apply that follows is additionally wrapped in a silent `try/catch` (lines 452–461) so its failures are invisible.

#### Paths that silently skip the GL post

1. **autoApply (Case B)** — `autoApplyAdvancePaymentsForTenant` is called in a try/catch where errors are caught and logged but do not fail the response (line 455–461). If auto-apply itself posts GL entries and fails, the caller never knows.
2. **arrears recovery fee** — also wrapped in a silent try/catch (lines 252–274). This is intentional per the comment, but means GL side-effects of the fee deduction can be silently dropped.

### A.2 `apps/web/src/app/api/payments/[id]/route.js` — PUT handler

#### Multi-step writes

**isUpfrontPayment branch** (line 120–150):
- Single `UPDATE payments` wrapped in `sql.transaction()` — correctly atomic.

**Invoice payment branch** (lines 239–301):
- `sql.transaction()` wraps: UPDATE payments, UPDATE payment_invoice_allocations, UPDATE invoices, UPDATE transactions (receipt row), UPDATE transactions (legacy commission row soft-delete) — **correctly atomic**.

> **Note:** The invoice payment branch pre-fetches linked transactions *outside* the transaction block (lines 210–216) due to a Neon HTTP client constraint requiring a synchronous query array. This is safe since the transaction re-reads what it needs.

#### isUpfrontPayment check and `oldPayment.invoice_id`

The `invoice_id` field is obtained via a `LEFT JOIN payment_invoice_allocations` (line 52–58), not from a column on the `payments` table. The `payments` table **does not have an `invoice_id` column** (confirmed by schema query — 25 columns, none named `invoice_id`).

```sql
-- payments table columns (relevant subset)
id, lease_id, tenant_id, property_id, payment_date, amount, currency,
payment_method, reference_number, period_month, period_year, recorded_by,
notes, is_reversed, reversed_by, reversed_at, created_at, deposited_at,
deposited_to_account_id, deposit_transaction_id, description,
approval_status, approved_by, approved_at, rejected_reason
```

For any payment with no allocation row, the `LEFT JOIN` returns `invoice_id = null`. So `isUpfrontPayment = !toNumber(null) = true` is always correct — but the variable name is misleading. An advance payment that has already been auto-applied (and thus *does* have an allocation) will have `isUpfrontPayment = false` and enter the invoice-payment update path, which correctly handles the allocation.

**Risk:** If a payment was recorded as an advance and subsequently allocated, editing it goes through the invoice path, which can update the linked GL transaction. That is correct behavior, but it is not obvious from the code.

### A.4 `autoApply.js` — `autoApplyAdvancePaymentsForTenant`

#### Write sequence

1. **STEP 1** — `sql.transaction()`: INSERT payment_invoice_allocations (ON CONFLICT DO UPDATE), UPDATE invoices per allocation. **Correctly atomic.**
2. Fetch allocation IDs for the just-inserted rows (outside transaction, safe).
3. **STEP 2** — `Promise.allSettled(postPromises)`: posts one GL entry per allocation. **Not transactional.** Each `postAccountingEntryFromIntents` call is independent.
4. **STEP 3** — `Promise.allSettled(feePromises)`: arrears recovery fees. Also independent.

#### Half-committed failure paths

If STEP 1 succeeds but any STEP 2 GL post fails:
- The allocation row and invoice update are permanently committed.
- No GL entry is created for that allocation.
- `Promise.allSettled` swallows the failure — the caller receives `{ ok: true }`.
- **The failure is invisible to the UI and to the batch trigger.**

If `allocationId` lookup returns `undefined` for any entry (line 199–204), GL posting is skipped with a `console.error` — again silent to the caller.

#### Parallel batch processing risk

`autoApplyAdvancePaymentsToOpenInvoices` processes tenants in batches of 5 in parallel (line 288). If two tenants share a payment (edge case), race conditions in the unapplied balance calculation are possible since the balance is computed outside the transaction.

## B. Ledger Gap Census

### B.1 Status buckets — approved, non-reversed payments

```sql
SELECT
  status_bucket,
  COUNT(*) AS payment_count,
  SUM(amount) AS total_amount
FROM (
  SELECT p.id, p.amount,
    CASE
      WHEN EXISTS (SELECT 1 FROM transactions t WHERE t.source_type = 'payment'
        AND t.source_id = p.id AND COALESCE(t.is_deleted,false) = false)
        THEN 'has_payment'
      WHEN EXISTS (SELECT 1 FROM transactions t WHERE t.source_type = 'payment_advance'
        AND t.source_id = p.id AND COALESCE(t.is_deleted,false) = false)
        THEN 'has_advance'
      WHEN EXISTS (SELECT 1 FROM transactions t WHERE t.source_type = 'payment_auto_apply'
        AND t.source_id IN (SELECT pia.id FROM payment_invoice_allocations pia
          WHERE pia.payment_id = p.id) AND COALESCE(t.is_deleted,false) = false)
        THEN 'only_auto_apply'
      ELSE 'no_ledger_at_all'
    END AS status_bucket
  FROM payments p
  WHERE p.is_reversed = false AND p.approval_status = 'approved'
) sub
GROUP BY status_bucket ORDER BY status_bucket;
```

### C.2 Historic scheme distribution

```sql
SELECT
  CASE
    WHEN p.id IS NOT NULL AND pia.id IS NULL THEN 'old_scheme: source_id=payment_id'
    WHEN pia.id IS NOT NULL AND p.id IS NULL THEN 'new_scheme: source_id=allocation_id'
```

### D.3 Cleanup-eligible entries (7)

These 7 ledger entries have `source_id` pointing to a **reversed** payment. The parent payment has `is_reversed = true`, meaning the payment itself was voided, but these auto_apply GL entries were never soft-deleted. They represent ghost accounting entries for transactions that no longer exist. Safe to soft-delete (`is_deleted = true`).

One additional entry exists for payment 463 (Arafat Sebaka) which is `is_reversed = true` and `approval_status = 'rejected'` — also cleanup-eligible.

### D.4 Needs-investigation entries (183)

These 183 entries point to approved, non-reversed payments with ≥ 1 allocation. They represent valid economic events. The problem is not the entries themselves but the sourceId scheme:

- **Correct economic effect:** Dr Tenant Prepayments / Cr Tenant Receivable (the right accounts)
- **Wrong idempotency key:** `source_id = payment.id` instead of `source_id = allocation.id`

**Consequence:** If auto-apply is re-run for any of these payments, the `postingAdapter` idempotency check uses `(source_type, source_id)`. Since the new scheme uses `source_id = allocation.id`, the old entries provide no idempotency protection — re-running will create a duplicate entry.

No entry in this set has a reversed/rejected parent, so none are safe to soft-delete without further investigation.

## E. Recommended Fix Order

### 1. Fix first — wrap `POST /api/payments` in a database transaction (HIGH impact, MEDIUM risk)

**Why highest priority:** The route.js POST handler performs 3 DB writes before calling the GL post. A GL failure after those writes leaves data inconsistent and is silently returned as a 500 — the payment exists but has no accounting entry. This is the root cause of some of the `no_ledger_at_all` and `only_auto_apply` cases.

**Recommended approach:** Wrap all DB writes and the GL post in a single unit that rolls back on failure, or — since GL post is external — perform the GL post *first* (with rollback on failure), then commit the DB writes.

**Risk:** Moderate. Requires changing the main payment creation path. Test Case A and Case B separately.

---

### 2. Fix second — backfill 192 advance payments missing auto_apply GL entries (HIGH impact, LOW risk if done carefully)

**Why urgent:** 192 payments (UGX 54.2M) have a `payment_advance` GL entry and allocation rows but no `payment_auto_apply` GL entry. Tenant Prepayments liability is overstated by UGX 54.2M. This is a live balance sheet error.

**Recommended approach:** Write a one-time migration script that, for each affected payment, posts the missing `Dr Tenant Prepayments / Cr Tenant Receivable` entry using the correct `source_id = allocation.id` scheme. Run in a staging environment first. The existing `postAccountingEntryFromIntents` idempotency check will prevent double-posting.

**Risk:** Low if the script is read-only first (dry run), then executed against production. Use `source_type = 'payment_auto_apply', source_id = allocation.id` so PR #7's idempotency check protects re-runs.

---

### 3. Fix third — soft-delete 7 ghost ledger entries for reversed payments (LOW impact, VERY LOW risk)

**Why:** Reversed payments should have had their GL entries soft-deleted. These 7 entries (UGX 1.15M) represent accounting transactions with no valid parent. They are cleanup-eligible.

**Recommended approach:** A targeted UPDATE setting `is_deleted = true, deleted_at = now()` for these 7 `transactions.id` values. No DB transaction needed. Verify via audit log.

---

### 4. Can wait — investigate and deduplicate 10 extra_ledger payments (MEDIUM impact, MODERATE risk)

**Why can wait:** The 10 payments with duplicate GL entries (UGX 4.07M) double-count revenue recognition but do not create uncovered liabilities. The ledger balances, just over-records the debit/credit pair.

**Risk in fixing:** Soft-deleting the duplicate requires identifying which entry is the duplicate (the second one) without disrupting deposit reconciliation. Investigate whether any of these 10 allocations have been deposited before touching them.

---

### 5. Investigate separately — 95 payments with old-scheme sourceId (INFORMATIONAL)

These 95 payments (UGX 29.5M) have `payment_auto_apply` entries with `source_id = payment.id`. The accounting effect is correct (right accounts, right amounts). The only risk is that re-running auto-apply will create duplicate entries since the old and new idempotency keys are different.

**Recommended approach:** Do not touch until the backfill (#2 above) is complete. After the backfill, run a query to confirm none of these payments now have two `payment_auto_apply` entries (one old-scheme, one new-scheme). If they do, soft-delete the old-scheme entry.
