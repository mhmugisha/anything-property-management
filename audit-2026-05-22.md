## Structural Correction vs. Yesterday's Audit

Yesterday's audit (2026-05-21) counted `payment_auto_apply` ledger coverage by checking whether `tx.source_id` appeared in a payment's allocation set — without verifying that the *description* of each entry matched the payment's *tenant*. Because `payments.id` and `payment_invoice_allocations.id` share an overlapping auto-increment sequence, an old-scheme entry for payment N (where `source_id = N = payment.id`) would be misread as a new-scheme entry for any payment whose allocation happened to have `id = N`. This produced phantom "coverage" for payments that had none, and phantom "over-coverage" for payments that were clean.

This audit applies the **Critical Disambiguation Rule**: a `payment_auto_apply` entry belongs to payment P if and only if `description LIKE '%' || tenant_name_of_P || '%'`, restricted to entries where `source_id = P.id` OR `source_id IN (allocation ids of P)`.

## Section B — Correct Ledger Coverage Census

```sql
-- Corrected census using description-based disambiguation
WITH alloc_totals AS (
  SELECT payment_id, SUM(amount_applied) AS total_allocated, COUNT(*) AS alloc_count
  FROM payment_invoice_allocations GROUP BY payment_id
),
primary_coverage AS (
  SELECT source_id AS payment_id,
    COUNT(CASE WHEN source_type='payment' THEN 1 END) AS pay_invoice_cnt,
    COUNT(CASE WHEN source_type='payment_advance' THEN 1 END) AS advance_cnt,
    SUM(CASE WHEN source_type='payment_advance' THEN amount ELSE 0 END) AS advance_amt
  FROM transactions WHERE source_type IN ('payment','payment_advance')
    AND COALESCE(is_deleted,false)=false GROUP BY source_id
),
true_auto_apply AS (
  -- A payment_auto_apply entry belongs to payment P if description contains P's tenant name
  -- AND source_id matches either the payment or one of its allocations
  SELECT p.id AS payment_id, SUM(tx.amount) AS auto_apply_amount
  FROM transactions tx
  JOIN payments p ON (
    tx.source_id = p.id
    OR tx.source_id IN (SELECT pia.id FROM payment_invoice_allocations pia WHERE pia.payment_id=p.id)
  )
  JOIN tenants te ON te.id = p.tenant_id
  WHERE tx.source_type = 'payment_auto_apply'
    AND COALESCE(tx.is_deleted,false) = false
    AND tx.description LIKE '%' || te.full_name || '%'
    AND p.is_reversed = false AND p.approval_status = 'approved'
  GROUP BY p.id
)
SELECT bucket, COUNT(*), SUM(payment_amount), SUM(total_allocated),
       SUM(auto_apply_amt), SUM(total_allocated - auto_apply_amt) AS sum_gap
FROM classified GROUP BY bucket;
```

## Section E — Recommended Backfill Plan

### E.1 Entries to Insert

These are the missing `payment_auto_apply` GL entries for advance payments with uncovered allocations. Each allocation that has no matching description-attributed auto_apply entry needs a new `Dr Tenant Prepayments / Cr Tenant Receivable` entry with `source_type = 'payment_auto_apply'` and `source_id = allocation.id` (new scheme — matches PR #7 idempotency key).

### E.2 Entries to Soft-Delete

**Category 1 — Payment_advance entries for reversed payments**

21 `payment_advance` GL entries (5,600,000 UGX) exist for payments where `is_reversed = true`. These represent liability credits that were never removed when the payment was voided.

```sql
SELECT COUNT(*), SUM(tx.amount)
FROM transactions tx JOIN payments p ON p.id = tx.source_id
WHERE tx.source_type = 'payment_advance' AND COALESCE(tx.is_deleted,false) = false
  AND p.is_reversed = true;
-- Result: 21 entries, 5,600,000 UGX
```

Action: `UPDATE transactions SET is_deleted=true, deleted_at=now() WHERE id IN (...)`.  
**Confidence: HIGH.** Reversed payments' GL entries should always be voided.

**Category 2 — Over-covered payment (352)**

Payment 352 (Musoke Richard, 320,000) has `payment_advance` posted for 350,000 and auto_apply of 350,000 — both 30,000 more than the payment amount and allocation. The 30,000 overage should be investigated: either the original advance amount was wrong (data entry), or there is a second allocation not yet recorded. Do not soft-delete without confirming which amount is correct.  
**Confidence: LOW — investigate first.**

**Category 3 — No_ledger_at_all entries**

14 non-reversed approved payments (2,060,000 UGX) have no GL entries at all. There is nothing to soft-delete; these need GL entries *inserted*. However, the correct entry type (invoice `payment` vs advance `payment_advance + auto_apply`) must be determined from the original payment intent (description clues: payments with "Payment on Account" description need advance treatment; "Rent for:" payments need invoice treatment).  
**Confidence: MEDIUM — needs per-payment classification.**

### E.3 Dual_primary_anomaly — HIGH RISK, REQUIRES INVESTIGATION

220 payments (67.4M) have both a `payment` ("Rent collection") and a `payment_advance` ("Payment on Account") GL entry. This is the dominant driver of the 77M Tenant Prepayments balance.

| Path | Action | Risk |
|---|---|---|
| **If payment is truly an invoice payment** | Soft-delete the `payment_advance` entry; reduce account 2150 by the advance amount | HIGH — removes large liability credit |
| **If payment is truly an advance payment** | Soft-delete the `payment` ("Rent collection") entry; insert missing `payment_auto_apply` entries for all allocations | HIGH — removes income recognition entry |

**These two paths have opposite effects on the P&L and balance sheet.** Do not proceed without reviewing each payment's original intent. A batch approach: filter by description — payments described as "Payment on Account" are likely advances; payments described as "Rent for:" are likely invoice payments. But confirmation should come from the original user who recorded them.

Sub-groups by urgency:
- 208 with no auto_apply: highest priority to classify and fix
- 10 with partial auto_apply: already partially treated as advances; likely safe to insert the remaining auto_apply entries once the `payment` entry is confirmed spurious
- 2 with full auto_apply: already fully treated as advances; only the `payment` entry is suspect

### E.4 Suggested Order of Operations

1. **Soft-delete 21 `payment_advance` entries for reversed payments** — zero ambiguity, reduces balance by 5.6M. (VERY LOW RISK)
2. **Insert 20 auto_apply entries for the 17 missing/partial pure advance payments** — use `source_id = allocation.id`. Reduces balance by 2,975,000. (LOW RISK)
3. **Classify and post GL entries for the 14 no_ledger_at_all payments** — per-payment classification needed. (MEDIUM RISK)
4. **Investigate and resolve the 220 dual_primary_anomaly payments** — work in batches by description type; run a dry-run showing the net P&L and balance sheet impact before committing. (HIGH RISK, do last)
